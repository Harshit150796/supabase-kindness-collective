# Admin portal rules
- Admin portal pages render inside AdminLayout (via DashboardLayout on /admin paths); lists use server-side pagination through DataTable, never whole-table loads.
- Admin mutations go through security-definer admin_* RPCs that re-check role (admin/staff/viewer) and write admin_audit_log; never rely on hidden buttons.
- Fundraisers are archived, not deleted; permanent delete only via admin_hard_delete_fundraiser with zero donations/coupons.
- No fundraiser UPDATE triggers; auto-tasks poll via admin-dispatch.
- One 5-minute pg_cron job calls admin-dispatch with a Vault secret; downstream dispatchers reject calls without it.
- Shared RecordWork attaches private notes and audited follow-ups to exact record identities; AdminRecordDrawer reads paginated exact-match histories so guest/outside donors never require fabricated accounts.
- Notification counts and read actions use useAdminNotifications with the owner-scoped admin_notification_state RPC; list rows never determine unread totals.
- Saved personal views store only non-sensitive list preferences; never persist search text, credentials or donor record identifiers.
- Access: AdminShell opens only for a team session that passed the hidden team sign-in's authenticator step (see the root AGENTS.md, Admin sign-in); everyone else gets the 404. Don't add a sign-in prompt or a link to /admin anywhere public.
- Admin portal pages render inside one nested AdminShell route (guards + persistent frame + Suspense in content); pages must not add their own route guards or lazy imports outside adminPages.ts.
- Fundraisers list (rebuilt Nov 12, 2026, founder request): AdminFundraisers reads admin_fundraiser_list (one call: photo, organizer, money raised by the public page's rule, gifts, coupons to send/ready/used, open reports, homepage place; server-side status, quick view, need, search, sort and pages; `_ids` for one or a few rows) and admin_fundraiser_counts (tab and chip counts). Both are team-only and built on _admin_fundraiser_rows (service-only). Table or Photos view (`layout`), quick views (`view`: review, coupons, reports, no_photo, short_story, no_gifts, close, funded, homepage, hidden, examples, real; the SQL rule is _admin_fundraiser_in_view and fundraiserList.ts mirrors its labels), a row menu, bulk approve/pause/make active/archive (each still one audited admin_fundraiser_action), CSV of the filter or the selection. The drawer (components/admin/fundraisers/FundraiserDrawer) steps through the page with J/K and shows the photo, money, coupons, a page check and what was asked for.
- Fundraiser photos in other lists: useFundraiserPhotos / FundraiserChip (components/admin/fundraisers/FundraiserChip) load the photos for one page of rows in one query, with the public site's photo rule. Used by Donations, Donated cards, Procurement, Messages, Verifications and the Dashboard.
- Dashboard "Needs attention" counts every queue in one place (fundraisers to review, coupons to send, codes to buy, donated cards, new contact messages, reports, verifications, monthly payment problems, open fundraisers without a photo, overdue tasks) and shows the oldest fundraisers waiting for review with their photos.
- Audit log: filters by person, area and dates; "What changed" lists only the fields that differ; codes, PINs and secrets show as (hidden) there and in its CSV.
