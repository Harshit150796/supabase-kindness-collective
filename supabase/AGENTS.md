# Backend security architecture

## Security rules (October 2026 audit; don't loosen these)
- Browsers never write money, status or review fields. Donations are inserted only by the payment webhooks and service-role code (no INSERT for anon/authenticated). Trigger guards keep server-side: fundraiser status, totals, featured_order, is_example, archive and rejection fields, owner and slug (trg_fundraiser_owner_guard, staff and security-definer RPCs pass); profiles.email and user_id (trg_profile_guard); verification review fields (trg_verification_guard); Gold Coin balances (trg_loyalty_card_guard, no browser UPDATE on loyalty_cards). Change these through admin RPCs or edge functions, never a client update.
- Team rows are invited, accepted and resent through fundraiser-actions; from the browser an organizer can only delete or revoke a co-organizer and a co-organizer can only leave (trg_fundraiser_team_guard stops moving a row to another fundraiser). Fundraiser updates are posted and screened through fundraiser-actions; browsers can only delete them.
- Accounts are created only by the create-account function, which needs a code verify-otp marked verified for that address in the last 15 minutes, and opens the account already confirmed; the site never calls supabase.auth.signUp. OTPs come from crypto.getRandomValues, and each code gets five tries through otp_check (counted under a row lock). Accounts it opens carry app_metadata.signup = 'create-account', and it lists the address in allowed_signups just before creating the account: once the site is published, the trg_signup_lock trigger on auth.users refuses any email account not listed there in the last ten minutes (Google sign-ins pass), so the Supabase sign-up API can't be used directly. To add an email user by hand, insert the address into allowed_signups first. Password-reset lookups use findAuthUserByEmail (every page of users). An unconfirmed account nobody has signed in to (opened through the sign-up API by someone who can't read the inbox) doesn't block the address: send-otp still sends a code and create-account replaces it (signupBlocked). New accounts join the mailing list when their email is confirmed (handle_new_user and the on_auth_user_email_confirmed trigger), not when the row is created.
- Functions with verify_jwt = false authenticate inside (_shared/auth.ts): staff tools use serviceOrStaff, the donor comes from requestUser (never a user id in the body), return URLs from returnOrigin, and secrets and signatures are compared with timingSafeEqual. Errors sent to browsers are generic; details go to the logs only.
- Rate limits go through overLimit, which calls rate_limit_take (count and record in one locked step). clientIp prefers cf-connecting-ip and counts IPv6 per /64. They cover card payments, checkout, OTP send and verify, account creation, password reset, consent sign-ups (per network plus a site-wide ceiling on new addresses) and the Coupon assistant (20 messages, 24 KB, 4 steps, 1024 output tokens). Card limits count only real declines (Square PAYMENT_METHOD_ERROR); a site-wide burst pauses guest card payments only, never signed-in donors or saved cards.
- Emails are matched with whereEmail (exact, no wildcards: the database API treats * like %) and checked with isEmail (the sign-up form's rule) in _shared/email-exists.ts; never pass an address straight into ilike. Guest gifts link only to an account that confirmed the same address.
- Newsletter click links carry a per-campaign signature (_shared/link-sign.ts); email-track-click forwards only signed links, our own site, or (emails sent before signing) a link in that campaign's own content, so it can't be used as an open redirect.
- The shared pool (claim_available_coupon) needs a verification a staff member approved in Admin > Verifications (an admin_write entry in admin_audit_log), or a live request while "Require approval" is on, plus a confirmed email; at most 2 claims a day and 5 waiting, under a per-person lock.
- Storage buckets accept only the image and video types the site uploads, with size caps (no HTML or SVG). Links taken from user data render through safeHref (src/lib/safeUrl.ts, http and https only); the newsletter preview is a sandboxed iframe; index.html carries a CSP meta (base-uri, object-src, form-action, upgrade-insecure-requests).
- Payment functions (create-donation-checkout, create-square-payment, square-webhook) deploy only when the site is published, webhooks first; create-stripe-checkout is retired (410).
- Public-profile columns (username, display_name, bio, avatar_url, cover_url, causes, links, visibility, pins, restrictions, hidden) change only through profile-actions or admin RPCs; trg_profile_guard keeps them from browser updates. follows, user_blocks and profile_notifications have no browser writes.
